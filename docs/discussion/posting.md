# Discord 投稿まわりの判断

> **2026-07-26 の作り直しで、この文書の多くが過去の記録になった。**
> スレッドの自動作成・Embed・投稿キュー・日次上限は廃止されている。
> 現在の仕様は [spec/04 取得と投稿](../spec/04-collection.md)、
> 廃止の理由は [削減の記録](reductions.md) を見ること。
> 以下、廃止された節には見出しに注記を付けてある。

## ボス別に分ける理由（**スレッド自動作成は 2026-07-26 に廃止**）

クラバト期間中は5体分の動画が同時に流れる。1チャンネルに混ぜると、
自分が今困っているボスの情報を探すのにスクロールが必要になる。
ボス別に分ければ、詰まっているボスのところだけ開けばよい。

**ボス別に分ける方針は残したが、投げ先はスレッドからチャンネルに変えた。**
Bot がスレッドを作るのをやめ、運用者があらかじめ作った既存チャンネルの ID を
`config.yaml` に書く形にした（`discord.boss_channels`）。作成・実在確認・
再起動時の復元がすべて不要になり、`period_state.boss_thread_ids` も消えた。
`layout` 設定（`single` / `per_boss_thread`）も分岐ごと廃止。

### トレモ動画と本番動画でスレッドを分けない理由

分けると**同じボスの情報が二箇所に散る。** 「4ボスの持ち越し編成」を探している人は、
それがトレモ撮影かどうかを問わず全部見たい。

当初は Embed 上のバッジで区別していたが、それも
[2026-07-26 に廃止した](classification.md#フルオート--手動--トレモ)。
トレモかどうかはタイトルを見れば分かる。

### 判定不能な動画を fallback チャンネルへ出す理由

複数ボスにヒットした動画を全ボスの投稿先に投げると、どこを開いても同じ動画が
目に入る。**どのボスにも属さない動画は、どのボスの場所にも置かない**のが素直だった。

ボス名が1つも当たらなかった動画も同じ扱いにする。既定では捨てずに投稿する（[スコープと方針](scope.md#取りこぼすくらいなら関係ない動画が混ざってよい)）。

投げ先は当初「親チャンネル」だったが、既存チャンネル指定に変えたことで
`fallback_channel_id` という独立した設定項目になった。**この設定は必須**にしてある。
未設定を許すと、判定不能な動画の投げ先が無くなって取りこぼすため。

## 動画の説明文を転載しない理由（**Embed は 2026-07-26 に廃止**）

**他人が書いた文章をそのまま再配布することになる。** 引用の範囲を超えるうえ、
説明文には投稿者の宣伝・SNS リンク・依頼事項などが含まれることが多く、
文脈から切り離して転載すると意図しない形で流通する。

タイトルとリンクだけなら、視聴者を元動画へ誘導する形になり、投稿者の利益とも一致する。
**使うことと再配布することは別**として扱った。

**この判断は Embed を廃止したあとも生きている。**投稿はタイトルと URL の2行だけで、
説明文には触れない。むしろ現在は判定にも説明文を使わない（タイトルのみを見る）。

## 日次投稿上限を設けた理由（**2026-07-26 に廃止**）

`max_posts_per_boss_per_day`（既定15件）。人気ボスに動画が集中した日に、
1ボスの投稿先が数十件で埋まると通知として機能しなくなる、という懸念から入れた。

**廃止した。**取得経路が `search.list` 1本になり、1巡で取れるのは最大50件、
そこから既投稿分を引いた残りしか投稿しない。**溢れる経路が無くなった**ため。
上限に伴う `filter_reason = "daily_limit"` と、JST 日付ごとの上限到達通知も同時に消えた。

## 期間終了時にキューを投げ切る理由（**キューごと 2026-07-26 に廃止**）

期間終了時点で未投稿が残っている場合、投げ切るか破棄するかを検討し、**投げ切る**を選んだ。
終了間際に投稿された動画も、その月の記録としては価値があるため。

**投稿キューそのものが無くなったので、この論点は消滅した。**現在は取得したその場で
投稿するため、`/stop` の時点で「未投稿分」という状態が存在しない。

## 429 のリトライを3回で打ち切る理由

`Retry-After` に従って待って再送するが、同一動画につき最大3回まで。

3回失敗する状況はレート制限ではなく別の問題（権限、チャンネル削除など）の可能性が高い。
無限に粘ると巡回全体が止まる。**諦めた動画は記録しない**ので、次の巡回で
検索結果に再び現れ、自然に再試行される。

`Retry-After` が付かない場合のみ既定5秒を使う。**値が `0` の場合は「即再送してよい」**
という意味なので、`0` を「値なし」と混同しないよう明示的に分けた。

## 投稿に成功した動画だけを記録する理由

投稿前に記録すると、送信に失敗した動画が「投稿済み」として残り、
**二度と再試行されない。** 取りこぼしは Bot の目的に直接反する
（[スコープと方針](scope.md#取りこぼすくらいなら関係ない動画が混ざってよい)）。

当初は全件を保存して `status` で `pending` / `posted` を管理していたが、
**「成功したものだけ記録する」に変えると状態管理そのものが不要になった**。
記録が無い＝まだ投稿していない、なので次の巡回が勝手に拾い直す。

逆に、投稿成功後・DB 更新前にプロセスが落ちると二重投稿になりうるが、
こちらは実害が小さいので許容した。
