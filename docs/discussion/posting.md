# Discord 投稿まわりの判断

## ボス別スレッドを既定にした理由

クラバト期間中は5体分の動画が同時に流れる。1チャンネルに混ぜると、
自分が今困っているボスの情報を探すのにスクロールが必要になる。

ボス別スレッドなら、詰まっているボスのスレッドだけ開けばよい。
`layout: "single"` も残してあるが、想定運用は `per_boss_thread`。

スレッド ID は `period_state.boss_thread_ids` に保存し、再起動時に再利用する。
毎回作り直すと同じ名前のスレッドが増殖するため。

### トレモ動画と本番動画でスレッドを分けない理由

分けると**同じボスの情報が二箇所に散る。** 「4ボスの持ち越し編成」を探している人は、
それがトレモ撮影かどうかを問わず全部見たい。Embed 上のバッジで区別できれば十分だった。

### まとめ動画を親チャンネルへ出す理由

3体以上にヒットした動画を全ボススレッドに投げると、どのスレッドを開いても同じ動画が
目に入る。まとめ動画は性質上どのボスにも属さないので、親チャンネルに置くのが素直だった。

ボス判定できなかった動画も同じ理由で親チャンネルへ出す。既定では捨てずに投稿する（[スコープと方針](scope.md#取りこぼすくらいなら関係ない動画が混ざってよい)）。

## 動画の説明文を Embed に転載しない理由

**他人が書いた文章をそのまま再配布することになる。** 引用の範囲を超えるうえ、
説明文には投稿者の宣伝・SNS リンク・依頼事項などが含まれることが多く、
文脈から切り離して転載すると意図しない形で流通する。

タイトルとリンクだけなら、視聴者を元動画へ誘導する形になり、投稿者の利益とも一致する。
判定には説明文を使うが、**使うことと再配布することは別**として扱った。

## 日次投稿上限を設けた理由

`max_posts_per_boss_per_day`（既定15件）。人気ボスに動画が集中した日に、
1ボスのスレッドが数十件で埋まると通知として機能しなくなる。

上限に達した分は破棄せず `status = "filtered"`, `filter_reason = "daily_limit"` として残す。
翌日以降に手で拾える余地を残すため。

### 上限到達通知を JST の日付ごとに出す理由

当初はプロセス起動中に1回だけ通知していたが、**上限は JST 深夜にリセットされる**ため、
複数日にわたるクラバトでは2日目以降が無言になっていた。「今日も上限に達した」ことが
運用者に伝わらず、上限値の調整判断ができない。

通知フラグを `(JST日付, cb_period, boss_index)` のキーで持つように直した。

## 期間終了時にキューを投げ切る理由

期間終了時点で未投稿が残っている場合、投げ切るか破棄するかを検討した。

**投げ切る**を選んだ。終了間際に投稿された動画は、次月のクラバトでも同じボスが
出るとは限らないが、その月の記録としては価値がある。破棄すると収集した意味が消える。

終了直前に大量に溜まっていると翌日まで投稿が続く可能性があるが、
日次上限があるので暴走はしない。

## 429 のリトライを3回で打ち切る理由

`Retry-After` に従って待って再送するが、同一動画につき最大3回まで。

3回失敗する状況はレート制限ではなく別の問題（権限、チャンネル削除など）の可能性が高い。
無限に粘るとキュー全体が止まる。諦めた動画は `pending` のまま残すので、
次の収集サイクルで自然に再試行される。

`Retry-After` が付かない場合のみ既定5秒を使う。**値が `0` の場合は「即再送してよい」**
という意味なので、`0` を「値なし」と混同しないよう明示的に分けた。

## `status = "posted"` を投稿成功後にだけ更新する理由

投稿前に更新すると、送信に失敗した動画が「投稿済み」として記録され、
**二度と再試行されない。** 取りこぼしは Bot の目的に直接反する
（[スコープと方針](scope.md#取りこぼすくらいなら関係ない動画が混ざってよい)）。

逆に、投稿成功後・DB 更新前にプロセスが落ちると二重投稿になりうるが、
こちらは実害が小さいので許容した。
