# 動画の取得まわりの判断

## RSS 監視をやめ、API 検索 1 本にした理由

**2026-07-26 に、チャンネル RSS（`feeds/videos.xml`）による監視を廃止した。**
運用者の判断による。

もともと RSS が主経路だった。クォータを消費しないので、既知の投稿者を 30 分間隔で
追いかけても無料で、Data API のクォータを新規発掘だけに使えたからである。

やめた理由は運用コストだった。RSS は監視先を `config.yaml` に手で並べて初めて機能する。
**そのリストを作り、育て、保守する作業が毎月発生する**のに対して、拾える動画は
検索と大きく重ならない。監視リストの初期値を作る手がかりが無いという問題は
`/suggest_channels` で補っていたが、その仕組み自体が RSS を維持するためだけに存在していた。

### 代償

| 失ったもの | 内容 |
|---|---|
| 無料の巡回 | 取得が従量課金（1巡100ユニット）になった |
| 既知チャンネルの確実な追跡 | 検索に出てこない動画は拾えない |
| 検索枠の余裕 | `maxResults=50` を全ボスで共有する（下記） |

`YOUTUBE_API_KEY` が必須になったのも代償のひとつ。以前は未設定でも RSS だけで
動いたが、いまは何も収集できないので起動を中止する。

## 全ボスを 1 つの OR クエリにまとめた理由

`search.list` は**結果件数によらず 1 回 100 ユニット固定**。ボスごとに 1 クエリ投げると
1 巡 500 ユニットで、1 日の予算 9,000 では 18 巡（80分間隔）が限界だった。
RSS を失ったうえに追従が 30 分から 90 分に落ちるのでは割に合わない。

5 ボスの名前を `OR` で 1 クエリにまとめると 1 巡 100 ユニットになり、
**30分間隔（48巡/日 = 4,800ユニット）でも予算に収まる。**RSS と同じ追従速度を維持できた。

代償は `maxResults=50` の枠を 5 ボスで共有すること。30 分間に投稿された「ボス名を含む
動画」が 50 件を超えると押し出されて取りこぼす。`order=date` なので、特定ボスの動画が
集中した時間帯は他ボスが押し出されうる。クラバト期間中の実際の投稿量なら滅多に
起きないと判断した。頻発するようなら `search_interval_minutes` を詰めれば
1巡あたりの新着が減る（予算にはまだ余裕がある）。

## 検索はボス名だけで行う

API 検索のクエリは**ボス名のみ**。当初は `"プリコネ クラバト {ボス名}"` としていたが、
これをやめた。

[2026年7月の実データ](../reference/priconne_cb_2026-07_full.html)を見ると、
**ゲーム名もクラバトの語も入らないタイトルが珍しくない。**

```
ワイバーン 水魔法v2 46585 m1
オルレオン 3.55くらい
ライデン妥協3.5 マス93 コネクトall15
4段階目 オルレオン 3.95億 目押し0
```

「プリンセスコネクトRe:dive」と正式名称で書く例もある。`"プリコネ クラバト"` を
AND 条件で足すと、これらが丸ごと検索結果から消える。

同じ理由で、**ボス名マッチにプリコネ文脈語を必須条件にしていない**（EX表記の判定だけは
必須にしている。あちらは番号だけでは識別力が無いため）。

### 代償: 無関係な動画が大量に混ざる

「ワイバーン」「ライデン」は一般名詞的で、ARK / Dark and Darker / KOF / ベイブレードなどで
広く使われる。実データ118件（ユニークタイトル）での判定結果は次のとおり。

| | 件数 |
|---|---|
| 正しく拾えた | 47 |
| 取りこぼし | 2 |
| **無関係を拾った** | **43** |
| 正しく無視 | 26 |

取りこぼし2件はタイトルにボス名が無いもので、本番では説明文も判定対象に入るため拾える見込み。

無関係43件はすべてボス名マッチによるもの。[スコープと方針](scope.md#取りこぼすくらいなら関係ない動画が混ざってよい)
の方針上これは許容範囲だが、投稿数の半分近くが ARK の動画になる。

**RSS 監視を廃止したことで、この数字はそのまま実運用に出る。**以前は「監視対象が
プリコネ実況者のチャンネルなので他ゲームの動画が入りにくい」という緩和要因があったが、
検索 1 本になった今はそれが無い。緩和手段は `title_ng_words` に運用者がノイズ源を
追加することだけになった。

`maxResults=50` の枠を無関係な動画が食う点でも影響がある（前述の取りこぼしリスク）。
運用ログを見て NG ワードを調整する前提とし、判定ロジック側では絞り込まない。

## `videos.list` を必ず経由する理由

**50件まとめて1ユニット**と極端に安い。ここで初めて取れる情報が判定の質を大きく左右する。

| 取れるもの | 用途 |
|---|---|
| `contentDetails.duration` | ショート動画・長時間配信アーカイブの除外 |
| `snippet.description` | 判定対象テキスト。検索結果では切り詰められている |
| `liveStreamingDetails` | 配信中・配信予定の除外 |
| `statistics.viewCount` | 現状は保存のみ（[品質フィルタ](#品質フィルタを入れない理由)を入れていないため未使用） |

先に DB の既知 ID で絞ってから `videos.list` に渡している。再収集した動画に対して
無駄にユニットを使わないため。

## 配信アーカイブを除外しない理由

配信中・配信予定は除外するが、**終了済みアーカイブ（`actualEndTime` あり）は残す。**

クラバト攻略は生配信で検証されることが多く、そのアーカイブは有用な情報源になる。
「配信」でまとめて弾くと、この層を丸ごと落としてしまう。

長すぎるアーカイブは `max_duration_seconds` で別途切っているので、
「配信かどうか」で弾く必要はなかった。

## 検索間隔をクォータから逆算した経緯

`search.list` は**1回100ユニット**。全ボスを1クエリにまとめたので1巡100ユニット。
1日の既定クォータは10,000で、`quota_limit_per_day` は安全マージンを取って9,000。

| 間隔 | 1日の巡回数 | 消費 |
|---|---|---|
| 10分 | 144回 | 14,400 ← 上限超過 |
| 20分 | 72回 | 7,200 |
| **30分** | **48回** | **4,800** |
| 60分 | 24回 | 2,400 |

30分を選んだのは、廃止した RSS 監視と同じ追従速度だから。`videos.list` の消費と
手動 `/collect` の余地も十分に残る。

なおボスごとに1クエリ投げる旧方式では1巡500ユニットで、同じ予算では80分間隔が
限界だった。OR にまとめた判断の詳細は前述。

## クォータ超過時に停止しない理由

上限に達したら検索をスキップするが、**Bot は停止しない。**次の巡回でまた判定し、
JST の日付が変われば自動的に再開する。

`quotaExceeded` エラーをリトライしないのも同じ判断。リトライしても回復せず、
その日のうちに復旧する見込みがないため、即座にその日の検索を打ち切る。

RSS があった頃は「検索を止めて RSS のみに縮退する」という逃げ道があったが、
検索1本になった今、上限に達した時間帯の動画は取りこぼす。予算に対して
既定の4,800ユニット/日は余裕があるので、通常運用では起きない想定。

## 品質フィルタを入れない理由

`videos.list` で再生数が安く取れるため、「再生数 N 未満は投稿しない」といったフィルタは
低コストで実装できた。検討した選択肢は3つ。

| 案 | 却下理由 |
|---|---|
| (a) フィルタなし | **採用** |
| (b) 投稿を N 分遅延させて再生数で足切り | 速報性と両立しない。クラバト初日の情報価値は時間で急速に減る |
| (c) チャンネル登録者数でホワイトリスト運用 | 新規・小規模チャンネルの良質な検証動画を落とす。監視リストの手動運用と役割が重複する |

投稿直後の動画は再生数がゼロに近い。この Bot が価値を出すのはまさにその「投稿直後」なので、
再生数による足切りは目的と正面から衝突する。

除外は尺・NGワード・ライブのみに留めた。`view_count` は保存だけしてあるので、
運用してみて必要になれば後から使える。
