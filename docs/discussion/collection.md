# 動画の取得まわりの判断

## RSS を主経路にした理由

チャンネル RSS（`feeds/videos.xml`）は**クォータを消費しない**。既知の投稿者を追いかける用途では
これで十分で、Data API のクォータを新規発掘だけに使える。

RSS の制約は次の2つで、いずれも許容できると判断した。

- **最新15件しか返らない** — 投稿頻度の高いチャンネルは取りこぼしうるが、ポーリング間隔を詰めれば実用上問題ない
- **`description` / 尺 / 再生数が取れない** — `videos.list` で補完する（後述）

ETag / `If-Modified-Since` による 304 応答を使っているのは、更新のないチャンネルへの
無駄な取得を避けるため。クォータには影響しないが、相手サーバーへの礼儀と転送量の節約になる。

## 検索はボス名だけで行う

API 検索のクエリは**ボス名のみ**。当初は `"プリコネ クラバト {ボス名}"` としていたが、
これをやめた。

[2026年7月の実データ](../reference/priconne_cb_2026-07_full.html)を見ると、
**ゲーム名もクラバトの語も入らないタイトルが珍しくない。**

```
ワイバーン 水魔法v2 46585 m1
オルレオン 3.55くらい
ライデン妥協3.5 マス93 コネクトall15
4段階目 オルレオン 3.95億 目押し0
```

「プリンセスコネクトRe:dive」と正式名称で書く例もある。`"プリコネ クラバト"` を
AND 条件で足すと、これらが丸ごと検索結果から消える。

同じ理由で、**ボス名マッチにプリコネ文脈語を必須条件にしていない**（EX表記の判定だけは
必須にしている。あちらは番号だけでは識別力が無いため）。

### 代償: 無関係な動画が大量に混ざる

「ワイバーン」「ライデン」は一般名詞的で、ARK / Dark and Darker / KOF / ベイブレードなどで
広く使われる。実データ118件（ユニークタイトル）での判定結果は次のとおり。

| | 件数 |
|---|---|
| 正しく拾えた | 47 |
| 取りこぼし | 2 |
| **無関係を拾った** | **43** |
| 正しく無視 | 26 |

取りこぼし2件はタイトルにボス名が無いもので、本番では説明文も判定対象に入るため拾える見込み。

無関係43件はすべてボス名マッチによるもの。[スコープと方針](scope.md#取りこぼすくらいなら関係ない動画が混ざってよい)
の方針上これは許容範囲だが、投稿数の半分近くが ARK の動画になる。
実運用では次の2つで緩和される想定。

1. **RSS が主経路**であること。監視対象はプリコネ実況者のチャンネルなので、そもそも他ゲームの動画が入りにくい
2. `title_ng_words` に運用者がノイズ源を追加できること

運用ログを見て NG ワードを調整する前提とし、判定ロジック側では絞り込まない。

## `videos.list` を必ず経由する理由

**50件まとめて1ユニット**と極端に安い。ここで初めて取れる情報が判定の質を大きく左右する。

| 取れるもの | 用途 |
|---|---|
| `contentDetails.duration` | ショート動画・長時間配信アーカイブの除外 |
| `snippet.description` | 判定対象テキスト。RSS では取れない |
| `liveStreamingDetails` | 配信中・配信予定の除外 |
| `statistics.viewCount` | 現状は保存のみ（[品質フィルタ](#品質フィルタを入れない理由)を入れていないため未使用） |

先に DB の既知 ID で絞ってから `videos.list` に渡している。再収集した動画に対して
無駄にユニットを使わないため。

## 配信アーカイブを除外しない理由

配信中・配信予定は除外するが、**終了済みアーカイブ（`actualEndTime` あり）は残す。**

クラバト攻略は生配信で検証されることが多く、そのアーカイブは有用な情報源になる。
「配信」でまとめて弾くと、この層を丸ごと落としてしまう。

長すぎるアーカイブは `max_duration_seconds` で別途切っているので、
「配信かどうか」で弾く必要はなかった。

## API 検索の間隔をクォータから逆算した経緯

`search.list` は**1回100ユニット**。ボス5体それぞれで検索するので1巡500ユニット。
1日の既定クォータは10,000。

| 間隔 | 1日の回数 | 消費 |
|---|---|---|
| 1時間 | 24回 | 12,000 ← 上限超過 |
| 2時間 | 12回 | 6,000 |
| **3時間** | **8回** | **4,000** |
| 6時間 | 4回 | 2,000 |

3時間を選んだのは、`videos.list` の消費と突発的な再取得の余地を残しつつ、
1日8回なら新規チャンネルの発掘に十分だと判断したため。`quota_limit_per_day` を
9,000（既定10,000より低め）にしてあるのも同じ理由の安全マージン。

## クォータ超過時に停止せず縮退させる理由

上限に達したら API 検索だけを止め、**RSS のみで運用を続ける。**

クラバトは期間限定で、止まっている間の情報は後から取り返せない。API 検索は新規チャンネルの
発掘用でしかないので、これを落としても既知チャンネルの追跡は続けられる。
「全部止まる」より「一部が縮退する」ほうが被害が小さい。

`quotaExceeded` エラーをリトライしないのも同じ判断。リトライしても回復せず、
その日のうちに復旧する見込みがないため、即座に縮退へ切り替える。

## 監視チャンネルの発掘

`config.yaml` の `channels` は運用者が手で設定する必要があり、初期リストを作る手がかりがない。

そこで `/suggest_channels` を実装した。**収集済み DB の集計のみ**で、
「ボス判定に成功した動画が多い順」に未監視チャンネルを提示する。
YouTube API を呼ばないので追加クォータはゼロ。

API 検索が新規チャンネルを見つけ、その実績を集計して監視リストに昇格させる、
という流れを想定している。

## 品質フィルタを入れない理由

`videos.list` で再生数が安く取れるため、「再生数 N 未満は投稿しない」といったフィルタは
低コストで実装できた。検討した選択肢は3つ。

| 案 | 却下理由 |
|---|---|
| (a) フィルタなし | **採用** |
| (b) 投稿を N 分遅延させて再生数で足切り | 速報性と両立しない。クラバト初日の情報価値は時間で急速に減る |
| (c) チャンネル登録者数でホワイトリスト運用 | 新規・小規模チャンネルの良質な検証動画を落とす。監視リストの手動運用と役割が重複する |

投稿直後の動画は再生数がゼロに近い。この Bot が価値を出すのはまさにその「投稿直後」なので、
再生数による足切りは目的と正面から衝突する。

除外は尺・NGワード・ライブのみに留めた。`view_count` は保存だけしてあるので、
運用してみて必要になれば後から使える。
