# 設計判断の記録

**なぜその仕様にしたか**を残す。仕様そのものは [`docs/spec/`](../spec/README.md) が正。

spec 側には「何をするか」だけを書き、理由・却下した案・トレードオフはここに置く。
仕様を変更するときは、まずここに理由を書いてから spec を直す。

> **2026-07-26 に全面的な作り直しを行った。**この配下の多くは、いま存在しない仕組みに
> ついての記録になっている。**現在の仕様を知りたいなら [`docs/spec/`](../spec/README.md) を、
> 何をなぜ消したかは [削減の記録](reductions.md) を先に読むこと。**
> 廃止された節には見出しに注記を付けてある。

| 文書 | 扱う範囲 |
|---|---|
| [削減の記録](reductions.md) | **まずここ。**何をなぜ削ったか。作り直しの経緯もここ |
| [スコープと方針](scope.md) | 何をやらないか、取りこぼしと誤爆のどちらを許容するか |
| [収集期間](schedule.md) | 状態を2値にした理由、`mode` を廃止し `/start` / `/stop` だけにした理由 |
| [動画の取得](collection.md) | API 検索1本にした理由、OR クエリ、検索間隔の逆算、品質フィルタを入れない理由 |
| [判定ロジック](classification.md) | 複数ヒットの扱い、実データで見つけた欠陥。EX表記・持ち越し判定は廃止済みの記録 |
| [Discord 投稿](posting.md) | ボス別に分ける理由、説明文を転載しない理由、投稿成功分だけ記録する理由 |

## 決定済みの論点

実装前に運用者へ確認して決めた項目。**作り直しで失効したものを含む**ので、
現状は「いま」列で判断すること。

| # | 論点 | 当時の決定 | いま |
|---|---|---|---|
| 1 | 収集開始の既定モード | `trigger` + 催促あり | `/start` / `/stop` のみ（[schedule.md](schedule.md#mode-を廃止した理由)） |
| 2 | EX表記を採用するか | 折衷案で採用（分類のみ） | **廃止。**判定はボス名マッチのみ（[classification.md](classification.md#ex表記の採否2026-07-26-に廃止)） |
| 3 | 品質フィルタの要否 | フィルタなし（速報性優先） | 有効。除外は NG ワードのみ（[collection.md](collection.md#品質フィルタを入れない理由)） |
| 4 | 期間終了後の未投稿分 | 投げ切る | **論点ごと消滅。**投稿キューが無い（[posting.md](posting.md)） |
| 5 | RSS 監視チャンネルの初期リスト | `/suggest_channels` を実装 | **廃止。**RSS ごと廃止（[collection.md](collection.md#rss-監視をやめapi-検索-1-本にした理由)） |
| 6 | 実行形態・投稿先・除外フィルタ | — | 常駐 Bot / 既存チャンネル指定 / NG ワードのみ（[reductions.md](reductions.md)） |
