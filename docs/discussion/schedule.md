# 収集期間まわりの判断

前提となるゲーム側の日程は [クランバトル](../game/clan-battle.md) を参照。

## 収集開始をトレーニングモード開始に合わせた理由

トレモ期間中に今月のボス構成が判明し、**この時点から検証動画が出始める**。
本番開始まで待つと、初日に必要な情報がすでに出揃っているのに Bot が拾えていない状態になる。

クラバト初日は「どの編成が通るか」の情報価値が最も高い時間帯なので、ここを取り逃すと
Bot の主目的が果たせない。

日付で自動起動していた頃はこれをオフセット計算で狙っていたが、現在は運用者が
トレモ開始に合わせて `/start` する（下記「`mode` を廃止した理由」）。

## 状態を「収集する / しない」の2値にした理由

**2026-07-26 に、トレモ期間と本番期間の区別を廃止した。**

当初は `idle` / `training` / `battle` の3状態を持ち、トレモ期間はポーリング間隔を広げていた。
その根拠は「トレモ期間は動画本数が少ないため」だったが、**これは事実に反していた。**
実際にはトレモ期間の方が検証動画は多く投稿される（[クランバトル](../game/clan-battle.md#トレーニングモード)）。

区別を残す動機を洗い直すと、いずれも成立しなかった。

| 区別の用途 | なぜ不要か |
|---|---|
| ポーリング間隔を変える | 前提が誤り。トレモ期間の方が動画が多いので、広げる理由がない |
| トレモ動画の推定（`training_evidence = "phase_only"`） | 「トレモ期間に収集した」は根拠として弱い。キーワード判定があれば足りる |
| 本番開始通知 | 運用者はゲーム内で本番開始を知っている。Bot が知らせる意味がない |

ゲームの進行状況と Bot の収集動作は本来無関係で、Bot が答えるべき問いは
「今収集すべきか」だけだった。3状態は概念を1つ増やしただけで何も駆動していなかった。

## `mode` を廃止した理由

**2026-07-26 に、`schedule.mode`（`offset` / `manual` / `trigger`）を廃止した。**
収集は `/start` で始まり `/stop` で終わる。それ以外の起動経路も終了条件も無い。

もともと `trigger` が既定だった。毎月 `bosses.yaml` を書き換えるという手作業がどのみち
発生するので、この作業と Bot の起動を1操作にまとめれば、**「ボス未設定のまま自動起動する」
という最悪の事故が構造的に起きなくなる**からで、この判断自体は変わっていない。
`/start` に `bosses.yaml` の内容確認ボタンを挟んでいるのも同じ理由。

問題は、既定が `trigger` なのに `offset` / `manual` が残っていたことだった。

- **日付での自動開始は、使うつもりがないのに事故のリスクだけ残していた。**
  `offset` に切り替えた月は、`bosses.yaml` の更新を忘れると前月のボス名で走り出す。
  `month` の一致チェックで止めてはいるが、そもそも経路が無いほうが確実
- 実際の開催日程は月ごとに前後する（[クランバトル](../game/clan-battle.md#開催スケジュール)）。
  末日基準のオフセットが常に当たる保証はなく、当たらない月のために
  `manual` モードと `/period set` という上書き手段をさらに用意していた。
  **ずれを吸収する仕組みが、ずれる前提の仕組みの上に乗っていた**
- モードが3つあると、`/status` を見て「今どのモードか」を確認しないと Bot の挙動が
  読めない。運用者が把握すべき状態が増えていた

### 終了日を無くし、`/stop` だけにした理由

`mode` を廃止すると、終了日を算出していた式（末日 − `end_offset_days`）も根拠を失う。
開始が日付から切り離されたのに終了だけ日付で決まるのは一貫しない。

安全弁として「開始から N 日で自動終了」を残す案も検討したが、採らなかった。
**運用者の判断で、開始と終了の両方を明示操作に揃えるほうが単純だから。**

代償として、**`/stop` を忘れると収集が止まらない。**クラバトは月1回なので、
最悪その月いっぱい RSS 巡回と API 検索を回し続け、クォータを消費する。
これは受け入れた上での構成であり、`/status` の「収集中」表示と経過時間が
気づく手がかりになる。

### 催促を廃止した理由

`trigger` の弱点は `/start` を忘れると収集が一切始まらないことで、以前は offset 式で
算出した開始日を過ぎても未 `/start` なら Discord へ1回だけ催促していた。

`mode` の廃止で offset 式そのものが無くなり、「いつ催促すべきか」を決める根拠が消えた。
催促のためだけに日付設定を残すのは本末転倒なので、催促ごと廃止した。

## 待機中はポーリングループを回さない

以前は待機中も `idle_check_interval_minutes`（既定60分）間隔でループを回していた。
担っていたのは「期間に入ったかの判定」（`offset` / `manual` の自動開始経路）と
「`/start` 催促の判定」の2つで、**どちらも廃止された。**

残った待機中の tick には仕事が無いので、ループ自体を止めることにした。
`/start` がループを起動し、`/stop` が止める。`idle_check_interval_minutes` も削除した。

再起動時は DB の `period_state.is_open` を見て、収集中だった場合のみループを起動する。
