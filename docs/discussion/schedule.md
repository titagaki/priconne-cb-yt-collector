# 収集期間まわりの判断

前提となるゲーム側の日程は [クランバトル](../game/clan-battle.md) を参照。

## 収集開始をトレーニングモード開始に合わせた理由

トレモ期間中に今月のボス構成が判明し、**この時点から検証動画が出始める**。
本番開始まで待つと、初日に必要な情報がすでに出揃っているのに Bot が拾えていない状態になる。

クラバト初日は「どの編成が通るか」の情報価値が最も高い時間帯なので、ここを取り逃すと
Bot の主目的が果たせない。

## 状態を「収集する / しない」の2値にした理由

**2026-07-26 に、トレモ期間と本番期間の区別を廃止した。**

当初は `idle` / `training` / `battle` の3状態を持ち、トレモ期間はポーリング間隔を広げていた。
その根拠は「トレモ期間は動画本数が少ないため」だったが、**これは事実に反していた。**
実際にはトレモ期間の方が検証動画は多く投稿される（[クランバトル](../game/clan-battle.md#トレーニングモード)）。

区別を残す動機を洗い直すと、いずれも成立しなかった。

| 区別の用途 | なぜ不要か |
|---|---|
| ポーリング間隔を変える | 前提が誤り。トレモ期間の方が動画が多いので、広げる理由がない |
| トレモ動画の推定（`training_evidence = "phase_only"`） | 「トレモ期間に収集した」は根拠として弱い。キーワード判定があれば足りる |
| 本番開始通知 | 運用者はゲーム内で本番開始を知っている。Bot が知らせる意味がない |

ゲームの進行状況と Bot の収集動作は本来無関係で、Bot が答えるべき問いは
「今収集すべきか」だけだった。3状態は概念を1つ増やしただけで何も駆動していなかった。

これに伴い `start_offset_days` の意味も変えた。以前は「本番開始が末日の何日前か」（5）で、
トレモ開始は `training_days_before`（3）を引いて求めていた。区別が無くなったので
**「収集開始が末日の何日前か」（8）に統合**した。計算結果は変わらない。

## 既定モードを `trigger` にした理由

`offset`（日付で自動開始）と `trigger`（`/start` で手動開始）を比較して、`trigger` を既定にした。

毎月 `bosses.yaml` を書き換えるという手作業がどのみち発生する。この作業と Bot の起動を
1操作にまとめれば、**「ボス未設定のまま自動起動する」という最悪の事故が構造的に起きなくなる。**
`/start` に `bosses.yaml` の内容確認ボタンを挟んでいるのはこのため。

`offset` を既定にすると、運用者が `bosses.yaml` の更新を忘れた月に、Bot が前月のボス名で
検索を始めてしまう。これはボス構成の月次検証（`month` の一致チェック）で防いではいるが、
そもそも自動で走らせないほうが確実だった。

### 催促を入れた理由

`trigger` の弱点は `/start` を忘れると収集が一切始まらないこと。忘れたことに気づく機会がない。

そこで `offset` 式で算出した開始日を過ぎても `/start` されていなければ、Discord へ催促を1回だけ
投稿することにした。**1回だけ**なのは、毎回鳴らすと通知として無視されるようになるため
（催促が鳴りっぱなしでは通知として機能しなくなるため）。

## 日程のずれへの対処

実際の開催日程は月ごとに前後する（[クランバトル](../game/clan-battle.md#開催スケジュール)）。
末日基準のオフセットが常に当たるとは限らない。

`trigger` モードでは開始日はそもそも `/start` の時刻なので影響を受けない。影響するのは
終了日（`end_offset_days` で算出）だけで、ずれる月は `manual` モードか `/period set` で
明示的に上書きする。

## 待機中もポーリングループを回している理由

待機中は YouTube へ一切通信しないが、ループ自体は `idle_check_interval_minutes`（既定60分）
間隔で回り続ける。この tick が担っているのは2つ。

1. **期間に入ったかの判定** — `offset` / `manual` モードでは期間が日付だけで決まるため、この再計算が自動開始の唯一の経路
2. **`/start` 催促の判定**

`trigger` モードの起動自体はこのループに依存しない。`/start` コマンドがループを外から
再起動するため、待機中に眠っていても即座に起きる。**手動起動は待たされない。**

ループを完全に止める案もあったが、止めると上記2つが同時に機能しなくなる。
待機中の tick が消費するのは日付計算とローカル DB の SELECT だけで、
**YouTube のクォータは1ユニットも使わない**ため、止める実利がなかった。
